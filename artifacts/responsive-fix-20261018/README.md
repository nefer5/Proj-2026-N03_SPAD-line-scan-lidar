# 桌面工作区与缩放适配 · 2026-10-18

已按用户最新反馈保留桌面左参数/右结果布局，并放宽应用总工作区；预算细节图和B/C矮窗口滚动已改。只修改网页展示、交互与对应文档，没有修改Python计算逻辑、YAML工况或算法配置。

## 最终行为

- **整体宽度**：A/SPAD共享页面、预算、B和正式列级C不再受原1600–1800px总宽上限约束，保留边距，右侧结果使用剩余空间；参数栏仍有合理宽度，不跟随超宽窗口无限拉长。
- **A评估/调试**：大于760 CSS px保持左侧参数和右侧图形同时可见；侧栏约300–420px。960px宽窗口也保留左右布局。只有≤760px使用固定的参数/结果切换，表单和历史结果均保留；切换不提交新采集，显示后重绘图形。较窄侧栏中运行按钮独占一行，避免按钮文字被挤断。
- **预算细节图**：根据细节区域自身宽度切换，≤1100px时卡片上下排列；双坐标图和成像图保留最小绘图宽度。极窄区域允许图卡局部横向滚动，不通过压小标注或改变坐标比例适配。
- **B/C矮窗口**：高度≤700px时压紧操作区，整个参数面板单层滚动，表单不再被头尾挤成一小块。运行、恢复、说明、导入导出均保留，可滚动访问；高度充足时沿用原滚动方式。

唯一行为定义见[界面规范](../../docs/design/ui-design-guidelines.md)，用户意图见[架构决策](../../docs/design/architecture-decisions.md)。本次没有将R05整体统一或C人工验收标为完成。

## 实测覆盖与结果

使用独立agent-browser会话，打开真实本地服务，执行表单/按钮交互并保存截图与DOM测量；并非仅检查CSS字符串。

| 场景 | CSS视口 | DPR | 结果 |
|---|---|---|---|
| 1080P约100%可用空间 | 1920×940 | 1 | 五页保留桌面工作区，无整页横向溢出 |
| 1080P约125%可用空间 | 1536×734 | 1.25 | 同上 |
| 1080P约150%可用空间 | 1280×600 | 1.5 | 左参数栏保留；预算细节图改为上下；B/C侧栏可滚动 |
| 1080P约200%/矮窗口压力测试 | 960×440 | 2 | 仍保留桌面左右布局；B/C表单可使用整个侧栏高度 |
| 超宽窗口 | 3440×1320 | 1 | 工作区利用新增宽度，参数栏宽度有界 |

视口高度为扣除系统/浏览器界面的代表性近似值，不对应特定机器的精确工具栏高度。五页是预算、A评估、A调试、B、正式列级C；25组基础组合，加细节、滚动和窄窗切换共38组测量/截图，详见[verification.json](verification.json)。

- A在1920/1536/1280/960/761px均验证左右两区可见，760px才切换。验证键盘切换、宽窄恢复、参数保留、同一结果对象和直方图窗口保留；切换时监测到新增采集POST为0。额外真实编辑距离为101m后点击运行，确认新结果配置为101m并转到窄窗结果区。
- 预算在1280px测试中，双坐标细节图由原约345px绘图宽扩展为约753px；960px下保持620px绘图宽，在卡内滚动。未改变图的物理单位、数据、科学坐标比例或Python公式。
- B在960×440下，将工作区滚到侧栏顶部、再向下编辑时，表单可见高度约408px；原先独立内层表单约133px。C同场景可见约410px，原约181px。这些比较针对侧栏已进入可用工作区的状态；页面顶部的标题仍需要正常纵向滚过。
- C默认全帧预览仍可能超过现有投影工作量限制，本次未改限额。为了验收有效计划下的真实UI，明确将独立测试会话的每帧列数设为4，并选择两列局部实验；保留原光学/背景，预览正常、无错误提示。不是修改应用默认值，也不宣称默认全帧问题已解决。
- 补查A、预算、B、C的浅色主题、普通reload、短侧栏底部导出操作可达性。见[extra.json](extra.json)、[补查脚本](extra.py)。最终A按钮排布的小修由该补查验证，主验证脚本中较早的截图以a-final系列为准。
- 主验证和补查均未记录页面JavaScript错误；当前资源指纹、no-store响应、旧资源URL回读经过检查。A和调试页普通刷新后重新加载当前版本，未要求强制刷新。

**验证边界**：本次在真实浏览器渲染中调整CSS视口和DPR，覆盖Windows缩放对布局空间与像素密度的代表性影响；没有修改Windows显示设置，也未完成真实OS缩放、浏览器原生页面缩放或跨显示器拖动的端到端验收。用户人工体验验收仍待。预算三维DPR动态更新问题及更广泛的跨平台统一不在本次三项修复范围内。
